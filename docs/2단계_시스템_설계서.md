## 3. 좌표계 및 피치 설계 (FR-01)

모든 좌표는 픽셀이 아닌 **0~100 백분율**이다. 피치 크기·화면 크기와 무관하게 동일한 데이터가 동작한다.

```
        x=0                                   x=100
         ┌─────────────────────────────────────┐  y=0   ← 상대 골문 (공격 방향)
         │             상대 진영                 │
         │ ─────────── 하프라인 ─────────────── │  y=50
         │              자 진영                  │
         └─────────────────────────────────────┘  y=100 ← 자팀 골문
```

| 축 | 0 | 100 | 비고 |
| --- | --- | --- | --- |
| `x` | 왼쪽 터치라인 | 오른쪽 터치라인 | 5채널은 x축을 분할 |
| `y` | 상대 골라인 | 자팀 골라인 | 값이 **작을수록 전진**. `pressingLineY`도 이 축 |

- 실측 환산 기준: 피치 105m × 68m. `y` 1% ≈ 1.05m, `x` 1% ≈ 0.68m. 콤팩트니스 수치 표기에 사용한다.
- **좌표는 항상 분석 대상 팀 기준으로 정규화한다.** 분석 대상 팀이 홈이든 원정이든, 그 팀은 언제나 `y=100`(자기 골문)에서 `y=0`(상대 골문) 방향으로 공격한다. 따라서 `match.analyzedTeam`(`home`/`away`)은 **어느 팀을 분석했는지 표시하기 위한 메타데이터일 뿐, 좌표 해석이나 피치 방향을 바꾸지 않는다.** 이 규칙이 없으면 압박 라인(최대 y)·공격 서드(y 0~33.3) 같은 계산이 분석 대상에 따라 뒤집혀야 하는데, 그렇게 설계하지 않는다.
- 렌더링은 SVG `viewBox="0 0 100 100"` + `preserveAspectRatio`로 처리해, 좌표를 변환 없이 그대로 사용한다. Canvas 대신 SVG를 쓰는 이유는 선수 노드가 개별 DOM 요소여야 Framer Motion 모핑(§8)과 드래그를 붙일 수 있기 때문이다.

### 3.1 채널 경계 (FR-03)

5채널은 균등 20% 분할이 아니라 **페널티 지역·골 지역 폭을 연장한 실제 기준선**으로 나눈다.

| 채널 | x 범위 | 기준 |
| --- | --- | --- |
| 좌측 측면 | 0 ~ 20 | 페널티 지역 좌측 라인 연장 |
| 좌측 하프스페이스 | 20 ~ 36.5 | 페널티 지역 ~ 골 지역 사이 |
| 중앙 | 36.5 ~ 63.5 | 골 지역 폭 연장 |
| 우측 하프스페이스 | 63.5 ~ 80 | |
| 우측 측면 | 80 ~ 100 | |

수직 방향은 오버로드 계산을 위해 3분할한다: 공격 서드 `y 0~33.3`, 중원 `33.3~66.7`, 수비 서드 `66.7~100`. 채널 5 × 서드 3 = **15개 구역**이 오버로드 판정 단위다.

## 4. 데이터베이스 설계 (SQLite)

```sql
CREATE TABLE analyses (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    match_name      TEXT    NOT NULL,
    home_team       TEXT    NOT NULL,
    away_team       TEXT    NOT NULL,
    match_date      TEXT    NOT NULL,             -- YYYY-MM-DD
    competition     TEXT,
    analyzed_team   TEXT    NOT NULL,             -- 'home' | 'away'
    formation       TEXT    NOT NULL,             -- '4-3-3'
    summary         TEXT,
    schema_version  INTEGER NOT NULL DEFAULT 1,
    created_at      TEXT    NOT NULL,
    updated_at      TEXT    NOT NULL
);

CREATE TABLE players (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    analysis_id  INTEGER NOT NULL REFERENCES analyses(id) ON DELETE CASCADE,
    client_id    TEXT    NOT NULL,                -- JSON의 players[].id
    name         TEXT    NOT NULL,
    number       INTEGER NOT NULL,
    role         TEXT,
    UNIQUE (analysis_id, client_id)
);

CREATE TABLE phases (
    id               INTEGER PRIMARY KEY AUTOINCREMENT,
    analysis_id      INTEGER NOT NULL REFERENCES analyses(id) ON DELETE CASCADE,
    phase_type       TEXT    NOT NULL,            -- 'base' | 'attack' | 'defense'
    pressing_line_y  REAL,                        -- NULL이면 자동 산출
    comment          TEXT,
    UNIQUE (analysis_id, phase_type)
);

CREATE TABLE positions (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    phase_id   INTEGER NOT NULL REFERENCES phases(id) ON DELETE CASCADE,
    player_id  INTEGER REFERENCES players(id) ON DELETE CASCADE,  -- 상대팀이면 NULL
    side       TEXT    NOT NULL,                  -- 'own' | 'opponent'
    slot       INTEGER NOT NULL,                  -- 상대팀 좌표의 순서 보존용 (0~10)
    x          REAL    NOT NULL,
    y          REAL    NOT NULL
);

CREATE INDEX idx_positions_phase ON positions(phase_id);
CREATE INDEX idx_analyses_updated ON analyses(updated_at DESC);
```

설계 메모:
- **`client_id`를 별도로 둔다.** JSON 안의 선수 id(문자열)는 프론트가 만들고, DB의 정수 PK와 별개다. 저장·재로드를 반복해도 JSON 쪽 id가 안 바뀌어야 모핑 애니메이션의 노드 동일성(§8)이 유지된다.
- **`side='opponent'`인 행은 `player_id`가 NULL이다.** 상대팀은 이름·등번호를 입력받지 않으므로(요구사항 FR-06) 좌표만 저장하며, `slot`으로 순서를 보존한다.
- SQLite는 기본적으로 FK를 강제하지 않는다. 커넥션마다 `PRAGMA foreign_keys=ON`을 실행해야 `ON DELETE CASCADE`가 동작한다(3단계에서 이벤트 리스너로 지정).
- 요구사항 §4.4의 "상대팀은 입력 시 11명 전원" 제약은 DB 제약으로 표현이 어렵다. **Pydantic(서버)과 zod(클라이언트) 양쪽 검증으로 강제**한다.

## 5. API 설계 개요 (FR-08)

기본 규칙:
- 베이스 경로 `/api`, 요청·응답 본문은 JSON.
- **서버는 snake_case, 프론트는 camelCase**를 쓰고, `lib/api.ts`에서 자동 변환한다.
- 분석 상세(`GET /{id}`)의 응답 본문은 요구사항 §5.1의 JSON 스키마와 **완전히 동일한 형태**다. 그래야 JSON 파일 가져오기(FR-07)와 서버 조회가 같은 파서를 공유한다.
- 오류는 `{"detail": "..."}` 형태(FastAPI 기본)로 반환한다.

| 메서드 | 경로 | 요청 | 응답 | FR |
| --- | --- | --- | --- | --- |
| `GET` | `/api/health` | — | `{"status":"ok"}` | FR-08 (가용성 확인) |
| `GET` | `/api/analyses` | — | 목록 요약 배열 | FR-08 |
| `GET` | `/api/analyses/{id}` | — | 분석 전체 JSON | FR-08 |
| `POST` | `/api/analyses` | 분석 전체 JSON | 생성된 분석(+id) | FR-08 |
| `PUT` | `/api/analyses/{id}` | 분석 전체 JSON | 갱신된 분석 | FR-08 |
| `DELETE` | `/api/analyses/{id}` | — | `204 No Content` | FR-08 |

목록 응답에는 좌표를 싣지 않는다(`id`, `matchName`, `homeTeam`, `awayTeam`, `matchDate`, `competition`, `updatedAt`만). 상세 규격은 3단계 문서에서 확정한다.

**갱신은 전체 교체(replace) 방식이다.** `PUT` 시 하위 `players`/`phases`/`positions`를 지우고 다시 삽입한다. 부분 갱신(PATCH)은 MVP에서 지원하지 않는다 — 편집 화면이 항상 분석 전체를 들고 있으므로 부분 갱신의 이득이 없다.

| 경로 | 화면 | 비고 |

| `/` | 편집기 (피치 + 분석 패널) | 진입 시 빈 상태 또는 마지막 편집본 |

## 7. 상태 관리 전략

두 종류의 상태를 명확히 분리한다.

| 구분 | 도구 | 대상 |
| --- | --- | --- |
| 서버 상태 | React Query | 분석 목록, 분석 상세 조회, 저장/삭제 뮤테이션, 서버 헬스 |
| 편집 상태 | Zustand (`analysisStore`) | 현재 편집 중인 분석 전체(경기정보·선수·국면별 좌표·코멘트), 선택된 국면, 레이어 토글 |

- 편집 상태를 React Query 캐시에 두지 않는다. 드래그 중 좌표가 초당 수십 회 바뀌므로, 서버 캐시와 섞이면 불필요한 무효화·재요청이 생긴다.
- 레이어 토글(5채널/하프스페이스/압박라인/콤팩트니스/오버로드)은 **분석 데이터가 아니라 화면 설정**이다. 저장 대상에서 제외하고 스토어의 별도 슬라이스에 둔다.
- 저장(FR-08)은 스토어의 현재 스냅샷을 §5.1 JSON으로 직렬화해 뮤테이션에 넘긴다. 직렬화 함수는 JSON 내보내기(FR-07)와 **동일한 함수를 공유**한다.

## 8. 국면 모핑 설계 (FR-02)

- 선수 노드는 Framer Motion의 `motion.g`로 렌더링하고, **React key는 반드시 `playerId`를 쓴다.** 배열 인덱스를 key로 쓰면 국면 전환 시 노드 동일성이 깨져 엉뚱한 선수끼리 위치를 교환하는 애니메이션이 나온다. 이 프로젝트에서 가장 만들기 쉬운 버그다.
- 선수 노드는 `<motion.g>`로 감싸고 **`animate={{ x, y }}`(transform)로 보간**한다. `circle`의 `cx`/`cy` 속성을 직접 애니메이션하지 않는다 — 속성 애니메이션은 매 프레임 레이아웃을 다시 계산시키고, 자식 요소(등번호 텍스트)가 함께 움직이지 않는다. `layout` 애니메이션은 SVG에서 신뢰도가 낮으므로 사용하지 않는다.
- 전환 사양: `duration 0.6s`, `ease: [0.4, 0, 0.2, 1]`. 국면 전환 중 다른 국면 버튼을 누르면 현재 위치에서 새 목표로 이어서 보간한다(Framer Motion 기본 동작).
- **Ghost View**: 전환 직전 국면의 좌표를 `opacity 0.25`의 정지 노드로 함께 렌더링하고, 이전 위치 → 현재 위치를 잇는 점선 경로를 그린다. 전환이 끝나고 2초 후 페이드아웃하거나, 토글로 고정할 수 있다.
- 애니메이션 진행 여부를 스토어의 `isMorphing` 플래그로 노출한다. PNG 내보내기(§10)가 이 값을 보고 대기한다.

## 9. 공간 시각화 레이어 설계 (FR-03)

레이어는 각각 독립 토글이며, 피치 SVG 위에 순서대로 겹친다: 채널 그리드 → 콤팩트니스 → 압박 라인 → 오버로드 → 선수 노드(항상 최상단).

| 레이어 | 산출 방식 | 데이터 요구 |
| --- | --- | --- |
| 5채널 그리드 | §3.1 고정 경계선 렌더링 | 없음(정적) |
| 하프스페이스 강조 | 채널 2·4 영역을 반투명 채색 | 없음(정적) |
| 압박 라인 | `pressingLineY` 값에 수평선. NULL이면 **GK를 제외한 자팀 선수 중 최대 y**로 자동 산출 | 자팀 좌표 |
| 콤팩트니스 | 자팀(GK 제외) 좌표의 bounding box를 그리고, 세로·가로 길이를 m로 환산 표기 | 자팀 좌표 |
| 오버로드 | §9.1 | **상대팀 좌표 필수** |

GK 판별은 `role` 문자열이 아니라 **y값이 가장 큰 선수 1명**으로 한다. 역할 문자열은 자유 입력이라 신뢰할 수 없다.

### 9.1 오버로드 계산

```
입력: 국면 phase (자팀 11 좌표, 상대팀 11 좌표)
출력: 15개 구역별 { own, opp, diff, level }

for each zone in (5채널 × 3서드):
    own = zone 안에 포함된 자팀 선수 수
    opp = zone 안에 포함된 상대팀 선수 수
    diff = own - opp
    level = diff >= 2 ? 'strong'
          : diff == 1 ? 'weak'
          : 'none'
```

- 경계선 위의 좌표는 **작은 쪽 구역에 포함**한다(하한 포함, 상한 배제). 즉 `x ∈ [20, 36.5)`이면 좌측 하프스페이스.
- `strong`은 진한 채색, `weak`는 옅은 채색, `none`은 렌더링하지 않는다. 수적 열세(diff < 0)는 MVP에서 표시하지 않는다.
- 상대팀 좌표가 없으면 이 레이어의 토글 자체를 비활성(disabled)으로 만들고, 툴팁으로 "상대팀 위치를 입력하면 사용할 수 있습니다"를 안내한다(요구사항 FR-03).

## 10. 이미지 내보내기 설계 (FR-05)

- 캡처 대상은 화면의 반응형 레이아웃이 **아니라**, 화면 밖에 고정 크기로 렌더링해 둔 `ShareCard` 노드다. 뷰포트에 따라 결과물이 달라지는 것을 막는다.
- 카드 규격: 1:1 = 1080×1080, 4:5 = 1080×1350 (px). 사용자가 비율을 고른다.
- 카드 구성: 상단 경기 정보 → 피치(현재 국면 + 켜져 있는 레이어) → 하단 텍스트.
- **하단 텍스트는 "현재 국면 코멘트"와 "종합 평가(`summary`)" 중 선택한다.** 국면별로 카드를 3장 뽑고 마지막에 종합 평가 카드 1장을 더 뽑는 것이 카드 뉴스의 일반적인 사용 흐름이므로, 종합 평가가 이미지로 나갈 경로가 반드시 있어야 한다. 이 선택지가 없으면 사용자가 입력한 `summary`는 앱과 JSON 안에만 남고 결과물에는 전혀 등장하지 않는다.
- 캡처 절차:
  1. `isMorphing`이 `true`면 완료까지 대기한다(§8).
  2. 웹폰트 로드 완료(`document.fonts.ready`)를 기다린다. 이걸 빠뜨리면 글자가 폴백 폰트로 찍힌다.
  3. `html-to-image`의 `toPng`를 `pixelRatio: 2`로 호출한다.
  4. 생성된 data URL을 `<a download>`로 저장한다.
- 화면 밖 배치는 `position: absolute; left: -9999px`를 쓴다. `display: none`이나 `visibility: hidden`은 html-to-image가 캡처하지 못한다.
