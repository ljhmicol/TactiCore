## 항목 상세

### 2. 국면 자동 재생 버튼

- **내용**: 기본→공격→수비를 일정 간격으로 자동 순환 재생(모핑 애니메이션 시연용). 재생 중 국면 탭 비활성화. 시연·발표·SNS용.
- **기술 메모**: `PHASE_TRANSITION_MS`(600ms) 기존 상수 재사용, 인터벌 1.5~2초 정도. 작업량 반나절.

### 3. 감독 프리셋 추가

- **내용**: 후보 — 무리뉴, 안첼로티, 투헬, 포체티노 등 + K리그 감독. `frontend/public/samples/managers/`에 JSON 추가 + `ManagerPresetPicker` 배열 등록이 전부.
- **유의**: 좌표는 공개 전술 분석 기반 재구성(실제 트래킹 아님) — 기존 프리셋과 같은 주석 유지. 감독 최신 이력(해임·이적)은 추가 시점에 다시 확인한다.

### 4. 상대팀 프리셋

- **내용**: 오버로드 레이어는 `opponentPositions`가 있어야 동작하는데 지금은 11개 점을 일일이 찍어야 함. 감독 프리셋에 상대팀 기본 대형을 옵션으로 포함하거나, 상대 포메이션만 따로 고르는 UI.
- **기술 메모**: 스키마 변경 불필요(`opponentPositions` 이미 optional로 존재). 미러링 로직(`addOpponents`의 y'=100-y) 재사용.

### 5. 타임라인 (매치 체인징 포인트)

- **내용**: 3국면 고정을 넘어 경기 시간 축에 체인징 포인트를 여러 개 찍고 시점별 대형 저장. "전반 23분 추격 상황" 재현.
- **기술 메모**: 프론트 스토어·zod가 이미 대비함 — `convertKeys`가 `phases` 맵 키를 보호하는 이유가 이 확장이다(`api.ts` 주석 참조). 국면 키가 `base/attack/defense`에서 벗어나도 깨지지 않음. DB `phases.phase_type`은 문자열이라 호환. UI(타임라인 바)가 주 공수.

### 6. GIF/영상 내보내기

- **내용**: 국면 전환 모핑 애니메이션 자체를 SNS용 GIF/MP4로. PNG 다음 자연스러운 확장.
- **기술 메모**: 프레임 캡처(html-to-image 반복)→인코딩은 무거움. gif.js(Web Worker) 또는 MediaRecorder(canvas 스트림) 중 택일. 조사 필요.

### 7. 분석 목록 고도화

- **내용**: 목록 화면에 썸네일 미리보기(base 국면 미니 렌더링), 제목·날짜 검색, 태그. 목록이 수십 개가 되면 필요.
- **기술 메모**: 썸네일은 저장 시점에 base 국면을 작은 PNG로 만들어 두는 방식(목록 조회 시 렌더링은 느림) — 백엔드에 파일 또는 BLOB 컬럼 필요.

### 8. 공유 링크

- **내용**: 저장된 분석의 읽기 전용 URL. 로그인 없이 열람만.
- **기술 메모**: 공개 배포 + 공개 조회 API 필요. 데이터가 공개된다는 점 사용자 동의 필요.

### 9. 실제 경기 명장면 프리셋 (StatsBomb OpenData)

- **내용**: 원래 원했던 "실제 경기 분석"의 부분 실현. StatsBomb OpenData(무료, GitHub 공개)의 이벤트 데이터에는 슈팅 순간 양 팀 전원의 실제 좌표(freeze frame)가 담겨 있어, 이를 국면 프리셋으로 변환하면 "2022 월드컵 결승 결승골 장면" 같은 실제 배치를 불러올 수 있음.
- **제약 (중요)**: 슈팅 장면 위주(전 경기 트래킹 아님), 좌표계 변환(StatsBomb는 0~120 × 0~80) 필요, 원본 JSON이 커서 사전 가공 스크립트 필요. 작업량 중~대.
- **연혁**: "실제 경기를 DB에서 검색해 자동 분석"은 2026-09-01 무료 API가 국면별 선수 좌표를 제공하지 않아 기각 → 감독 프리셋으로 대체. 이 항목은 그 대안의 확장.

### 10. 배포 (Docker)

- **내용**: 저장소 루트의 `Dockerfile`/`docker-compose.yml`(백엔드 이미지 + `./data` 볼륨 마운트)은 이미 존재. 남은 결정: 프론트 빌드 산출물을 백엔드 이미지에 정적 서빙으로 포함할지 별도로 둘지.
- **기술 메모**: 컨테이너에서 `npm run build` → FastAPI가 `dist/`를 StaticFiles로 서빙하는 단일 이미지 구성이 가장 단순. 개발은 계속 로컬 2프로세스.

### 11. 로그인/계정

- **내용**: 분석 목록을 사용자별로 분리. 로컬 1인용인 동안은 의미가 제한적이라 배포 이후로 미룸.

### 12. 커뮤니티/댓글

### 16. 전술 대결(매치업) 뷰 — 저장된 전술 2개 대전

- **상태**: 2026-09-01 사용자 제안 ("내가 만든 전술 2개를 서로 경기 시켜보는 것") → 2026-09-07 구현 완료(`[O]`), 사용자 브라우저 확인 전
- **내용**: 저장된 분석 2개를 골라 한 피치에 오버레이. 전술 A의 **공격 국면** vs 전술 B의 **수비 국면**을 겹쳐 보여주고, 버튼으로 교대(A 공격 × B 수비 ↔ B 공격 × A 수비)한다. "내 4-3-3 공격이 상대 4-4-2 로우블록을 어떻게 깨는지" 검증용.
- **기술 메모(정정, 2026-09-07)**: 이전 메모("좌표 규약이 이미 통일돼 있어 미러 변환 불필요")는 **틀렸다**. 저장된 분석은 항상 "자팀 골 = y=100" 기준이라 두 분석을 그대로 겹치면 양쪽 다 자기 골문이 같은 지점(y=100)에 겹쳐 버린다. B(상대로 지정된 쪽)는 `lib/coords.ts`의 `mirrorPoint`로 **180도 회전**(`x'=100-x, y'=100-y`, x·y 둘 다 뒤집는다)해서 B의 골문이 A가 공격하는 방향(y=0)에 오도록 맞춘 뒤에야 오버로드 15구역 계산이 의미 있어진다(안 그러면 A는 항상 공격 3분의1, B는 항상 수비 3분의1에만 있어 겹치는 구역이 0이 됨). y만 뒤집으면 좌우 플랭크가 실제와 반대로 그려지므로 x도 함께 뒤집어야 한다.
- **구현 메모**:
  - `lib/coords.ts`에 `mirrorPoint` 추가(180도 회전, 자기 자신이 역함수 — 두 번 적용하면 원래대로). `lib/coords.test.ts` 신규
  - `components/pitch/StaticPlayerNode.tsx` 신규 — PlayerNode/OpponentNode는 `useAnalysisStore`에서 현재 활성 분석의 formation·index·드래그 액션을 끌어오는데, 대결 뷰의 두 분석은 활성 분석이 아니므로 재사용하면 안 됨(조용히 스토어에 로드된 엉뚱한 분석 색을 그리게 됨). formation·index를 props로 직접 받는 읽기 전용 노드. A=채움 원, B=흰 배경+색 테두리(겹쳐도 눈으로 구분되도록)
  - `components/versus/MatchupView.tsx` — ChannelGrid·CompactnessBox·PressingLine·OverloadLayer는 store에 묶이지 않은 순수 함수형 컴포넌트라 그대로 재사용 가능. 오버로드는 A를 own, 미러링한 B를 opponentPositions로 구성한 합성 PhaseData를 기존 `computeOverload`에 그대로 넘김. 압박 라인은 "수비하는 쪽"만 표시(그 블록이 어디서 시작되는지가 이 뷰의 관심사) — 콤팩트니스는 A/B 중복 표시가 의미 없어 스코프에서 제외
  - `routes/VersusPage.tsx` + `/versus` 라우트, 저장 목록과 마찬가지로 서버 조회가 필요해 `useServerHealth`로 게이트
  - 화살표(annotations)는 스코프 밖 — 22명이 이미 밀도가 높아 추가하면 산만함
  - 항목 2(자동 재생) 로직은 흡수하지 않음 — 수동 교대 버튼만 구현. 좌표계가 이 기능의 핵심이라 타이머 없이 검증하는 게 먼저
  - **범위 밖**: 실제 스코어·볼 시뮬레이션 — 확률 기반 가짜 점수는 "경기 시켜보기"의 기대를 배신하기 쉬워 포함하지 않음. 원하면 3차에서 가벼운 버전(예: 압박라인·오버로드 기반 우위 하이라이트) 별도 검토
- **검증**: vitest 51개(9 파일, mirrorPoint 왕복·고정점 테스트 포함)·eslint·tsc 클린. Playwright로 실제 저장된 두 프리셋(과르디올라 vs 이정효-수원)을 `/versus`에서 선택해 스크린샷 확인 — B(수원삼성) GK #30이 원본에서 y≈88(자기 진영)인데 화면에서는 y≈4~12(A가 공격하는 쪽)에 위치, 좌우 풀백(김민우 #23·정동윤 #32)도 반대 플랭크로 뒤집힘 확인. 교대 버튼으로 A/B 공수 전환 시 압박 라인이 방금 수비로 바뀐 쪽으로 옮겨가는 것도 확인
- **버그 수정(2026-09-07)**: "각팀의 수비 라인이 압박 라인인데 그게 각팀으로 반영이 안된더같아 교대될때" — 실제로 재현됨(B가 수비일 때 압박 라인이 항상 "매우 낮음"에 고정). 원인은 백엔드에서 불러온 분석의 미설정 `pressingLineY`가 `undefined`가 아니라 `null`로 와서(Python `None`→JSON `null`), `!== undefined`만 검사하던 코드가 `100 - null`(JS가 null을 0으로 강제 변환해 100)을 계산해버린 것. `lib/coords.ts`에 `resolveDefendingPressingLineY` 헬퍼로 뽑아 `== null`로 정정 + 회귀 테스트 추가. 커밋 `e91c7d1`

  - `lib/annotations.ts`에 `curvedArrowGeometry` 추가 — 2차 베지어. 부풀리는 방향은 사용자가 고르지 않고 **피치 중앙(x=50)에서 더 멀어지는 쪽으로 자동** 선택(오버랩은 대부분 터치라인 쪽으로 돎). 화살촉 방향은 시작→끝 직선이 아니라 "제어점→끝점" 접선을 쓴다 — 직선 방향을 그대로 쓰면 곡선 끝에서 화살촉이 삐딱해 보인다. 기존 `arrowGeometry`와 같은 균일 축척(K) 공간에서 계산 후 되돌림
  - `ToolPalette`에 "곡선" 토글 버튼 추가(움직임·패스 도구에서만 노출) — 별도 도구가 아니라 기존 도구에 걸리는 보조 스위치. `DrawOverlay`가 그리는 중 미리보기도 곡선으로 보여줌(확정 후와 그리는 중 모양이 다르면 헷갈림)
- **구현 — 패스 공 애니메이션**:
  - 스키마 변경 없음(순수 렌더링) — `pass` 타입 화살표마다 `from`→`to`를 왕복하는 `motion.ellipse` 추가(1.1초, 무한 반복, 0.6초 대기 후 재시작)
  - 곡선 패스는 직선 보간이 아니라 `bezierPoint`로 베지어 위 8개 점을 샘플링해 keyframe으로 써서 실제 곡선을 따라가게 함(직선 보간을 쓰면 공이 곡선을 가로질러 뚫고 지나가 버림)
  - PNG 캡처는 애니메이션 완료를 기다리지 않고 그 순간 상태를 그대로 찍는다 — 무한 반복이라 매번 다른 위치에서 캡처되지만 "패스 경로 위 어딘가의 공"은 정적 이미지로도 자연스러워 별도 처리 안 함
- **검증**: vitest 67개(annotations.test.ts에 curvedArrowGeometry 4개 + curved 스키마 파싱 1개 추가)·eslint·tsc·빌드 클린. Playwright로 실제 곡선 화살표를 그려서 화면에 바깥쪽으로 부푼 모양 확인, JSON 내보내기에서 `curved: true` 보존 확인, 백엔드 저장→목록에서 재로드까지 거쳐도 `<path>` 요소(곡선)로 남아있는 것 확인(DB 마이그레이션 정상 동작 검증), 패스 공이 실제로 위치를 옮기는 것(스크린샷 두 시점 비교) 확인
