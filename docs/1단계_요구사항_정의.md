# 1단계: 요구사항 정의서 (TactiCore)

## 1. 프로젝트 개요

### 1.1 프로젝트명
TactiCore — 축구 전술 시각화 툴

### 1.2 목표
축구 전술 분석을 정적인 스크린샷이 아니라, 국면별 대형 변화·공간 점유·압박 구조를 **인터랙티브하게** 보여주는 전술 시각화 툴을 만든다.

### 1.3 성공 기준
- 사용자가 한 번의 클릭으로 전술 국면(기본/공격/수비)을 전환할 수 있다.
- 5채널, 하프스페이스, 압박 라인, 오버로드를 시각적으로 확인할 수 있다.
- 완성된 분석 결과를 SNS 카드 뉴스용 이미지(PNG)로 바로 내보낼 수 있다.

### 1.4 범위 (MVP 기준)
- 축구장 피치 위 선수 배치 및 표시 (포메이션 프리셋 자동 배치 + 드래그 미세 조정)
- 3개 국면(기본 라인업 / 공격 시 / 수비 시) 전환 버튼과 모핑 애니메이션
- 공간 중심 시각화 레이어(5채널, 하프스페이스, 압박 라인, 콤팩트니스, 오버로드 하이라이트) 토글
- 국면별 전술 설명 텍스트 입력창
- 분석 화면을 SNS 카드 규격 PNG 이미지로 다운로드
- 분석 데이터 JSON 내보내기 / 가져오기
- 경기별 분석 데이터 DB 저장 및 목록 조회 (로컬 서버 + SQLite)

### 1.5 범위 제외 (2차 업데이트 예정)
- 회원가입 / 로그인 및 사용자별 데이터 분리
- 클라우드 배포(공개 URL) — MVP는 PC 로컬 실행 전용
- 타임라인 기반 매치 체인징 포인트(자유 시점 드래그 + 시점별 포메이션/메모)
- 댓글 및 커뮤니티 공유
- 실시간 경기 데이터 자동 수집, 선수 트래킹 데이터 연동, 영상 분석 자동화

> 국면 전환 버튼(3개)과 타임라인 기능은 별개 기능이다. MVP는 고정된 3개 국면 버튼만 제공하며, 자유 시점 타임라인은 2차 업데이트에서 별도로 구현한다.

## 2. 기술 스택

분석 데이터를 영구 저장하고 목록으로 조회하기 위해 **프론트엔드 + 로컬 백엔드(FastAPI) + SQLite** 구성으로 진행한다. MVP는 공개 배포 없이 PC에서 로컬 실행하는 것을 전제로 한다.

### 2.5 2차 업데이트 예정 스택
- 인증: FastAPI 기반 로그인/세션 (사용자별 데이터 분리)

## 3. 기능 요구사항

### 3.1 피치 및 선수 배치 (FR-01)
- 축구장 피치를 SVG/Canvas 기반으로 렌더링한다.
- 11명 선수를 노드(아이콘 + 등번호)로 피치 위에 배치한다.
- 각 선수 노드는 이름, 등번호, 기본 역할(포지션)을 표시한다.
- **선수 노드를 마우스로 드래그하여 위치를 수정할 수 있다.** 수정된 좌표는 현재 선택된 국면의 좌표로 반영된다.

### 3.2 원클릭 국면 모핑 애니메이션 (MVP, FR-02)
- 기본 라인업 / 공격 시 / 수비 시, 총 3개 국면 전환 버튼을 제공한다.
- 국면 전환 시 선수 노드가 즉시 이동하지 않고 부드럽게 모핑(위치 보간 애니메이션)한다.
- Ghost View: 전환 전 위치를 반투명 잔상으로 표시해 이동 경로를 보여준다.
- MVP 완료 기준: 2개 이상 국면 전환 + Ghost View 동작.

### 3.3 공간 중심 시각화 툴 (MVP, FR-03)

> Notion 원문에서 '1차 MVP 필수 기능' 목록과 '기능별 상세 페이지' 표의 MVP 기준이 상충했으나, **오버로드를 포함한 공간 시각화 전체를 MVP에 포함**하는 것으로 확정했다.

- 5채널 그리드(세로 5분할)를 토글로 켜고 끌 수 있다.
- 하프스페이스 영역을 강조 표시할 수 있다.
- 압박 라인(수비 라인 높이)을 선으로 표시한다.
- 콤팩트니스(팀 간격)를 시각적으로 표현한다.
- 특정 구역의 수적 우위(오버로드)를 하이라이트로 표시한다. '수적 우위'는 상대팀 선수 위치와의 비교로 산출되므로, 상대팀 좌표가 입력된 경우에만 활성화된다(§5 스키마의 `opponentPositions`).
- 상대팀 좌표가 없는 분석에서는 오버로드 레이어를 비활성(회색) 처리하고, 나머지 레이어(5채널/하프스페이스/압박 라인/콤팩트니스)는 자팀 데이터만으로 동작한다.
- MVP 완료 기준: 그리드 토글 + 오버로드 하이라이트 + 압박 라인 표시.

### 3.4 전술 설명 텍스트 입력 (MVP, FR-04)
- 국면(기본/공격/수비)별로 핵심 전술 코멘트를 입력할 수 있는 텍스트 입력창을 제공한다.
- 종합 평가를 별도로 입력할 수 있다.
- 텍스트 입력은 현재 선택된 국면과 연동된다(국면 전환 시 해당 국면의 코멘트가 표시된다).
- 입력값은 분석 저장(FR-08) 시 DB에 함께 저장되며, 이미지 내보내기 시 카드에 함께 렌더링된다.

### 3.5 이미지 내보내기 (MVP, FR-05)
- 분석 결과를 PNG 이미지로 캡처해 다운로드한다.
- SNS 공유용 **고정 비율 카드(1:1 또는 4:5)** 를 별도 렌더링 노드로 구성하여 캡처한다. 화면에 보이는 반응형 레이아웃을 그대로 캡처하지 않는다 — 뷰포트 크기에 따라 결과물이 달라지는 것을 방지하기 위함이다.
- 캡처 시점에 모핑 애니메이션이 진행 중이면 중간 프레임이 캡처될 수 있으므로, 애니메이션 완료 후 캡처를 수행한다.
- 카드에는 피치(현재 국면)와 텍스트가 함께 포함되며, 텍스트는 **해당 국면의 전술 코멘트 또는 종합 평가 중 선택**한다(종합 평가도 이미지로 내보낼 수 있어야 한다).

### 3.6 분석 작성 흐름 (MVP, FR-06)
- 새 분석 생성 시 포메이션 프리셋(4-3-3, 4-4-2, 4-2-3-1, 3-5-2 등)을 선택하면 11명이 피치에 자동 배치된다.
- 자동 배치된 선수 노드를 드래그하여 위치를 미세 조정한다(FR-01).
- 각 선수의 이름, 등번호, 역할을 입력/수정할 수 있다.
- 국면(기본/공격/수비)을 선택한 상태에서 편집하면 해당 국면의 좌표로 저장된다.
- 상대팀 좌표는 선택적으로 입력할 수 있으며, 입력 시 오버로드 레이어(FR-03)가 활성화된다.

### 3.7 JSON 내보내기 / 가져오기 (MVP, FR-07)
- 현재 작성 중인 분석 전체(경기 정보 + 선수 + 국면별 좌표 + 텍스트)를 `.json` 파일로 내보낸다.
- 내보낸 `.json` 파일을 다시 불러와 편집을 이어서 할 수 있다.
- 가져오기 시 §5 스키마에 대한 검증을 수행하고, 형식 오류 시 사용자에게 오류 위치를 안내한다.
- 레포에 번들된 샘플 경기 JSON도 동일한 경로로 로드된다.
- 내보내기/가져오기는 DB 저장(FR-08)과 별개의 백업·이관 수단이다.

### 3.8 분석 저장 및 목록 조회 (MVP, FR-08)
- 작성 중인 분석을 로컬 서버 API를 통해 SQLite DB에 저장한다(신규 저장 / 덮어쓰기).
- 저장된 분석 목록을 조회한다. 목록에는 매치명, 홈/원정팀, 경기일자, 최종 수정일시를 표시한다.
- 목록에서 분석을 선택해 불러오고, 이어서 편집할 수 있다.
- 저장된 분석을 삭제할 수 있다(삭제 전 확인).
- MVP는 단일 사용자 전제이므로 사용자 구분·권한 검사를 하지 않는다(2차에서 로그인과 함께 도입).
- 백엔드 서버가 실행 중이지 않으면 저장/목록 기능은 비활성화되고, 사용자에게 서버 미실행 상태를 안내한다. 이 경우에도 편집·PNG 내보내기·JSON 내보내기(FR-05, FR-07)는 정상 동작해야 한다.

### 3.9 (2차 업데이트) 타임라인 기반 매치 체인징 포인트
- 경기 시간대를 자유롭게 드래그하며 특정 시점의 포메이션과 메모를 기록/조회한다.
- 감독의 경기 중 전술 수정 흐름을 시간순으로 추적한다.
- 3.2의 고정 3국면과 달리, 임의 개수의 시점을 추가할 수 있는 확장 기능이다.

### 3.10 (2차 업데이트) 계정 및 커뮤니티
- 회원가입 / 로그인, 사용자별 데이터 분리
- 댓글 및 커뮤니티 공유
- 공개 URL 배포

## 4. 비기능 요구사항

### 4.1 UI/UX
- 라이트 모드만 지원한다 (다크 모드는 2차 업데이트 고려).
- 지원 언어는 한국어만으로 한다 (다국어는 2차 업데이트 고려).
- 데스크톱 뷰: 좌측 인터랙티브 피치 + 우측 국면 전환 탭/텍스트 입력 패널.
- 모바일 뷰: 상단 피치 + 하단 국면 전환 탭/스크롤 분석 영역 (반응형 레이아웃 필수).

### 4.2 호환성
- 데스크톱: 최신 버전의 Chrome, Safari를 기준으로 동작을 보장한다.
- 모바일: 최신 버전의 iOS Safari, Android Chrome을 기준으로 동작을 보장한다 (§4.1의 모바일 뷰가 필수 요구사항이므로 포함).
- 그 외 브라우저(Firefox, Edge 등)는 별도 보장하지 않는다 (2차 업데이트 시 확대 고려).

### 4.3 성능
> 원문(Notion)에 성능 수치가 명시되어 있지 않아, 아래 수치는 작성자 가정값이다. 검토 후 조정 가능.

- 국면 전환 애니메이션은 60fps에 가깝게 부드럽게 동작해야 한다 (Framer Motion 기본 easing 활용).
- 이미지 내보내기(PNG 캡처)는 3초 이내에 완료되어야 한다.
- 로컬 API 응답(저장/목록/조회/삭제)은 500ms 이내에 완료되어야 한다.

### 4.4 데이터 무결성
- 국면별 좌표(x, y)는 0~100 범위의 백분율 값으로 제한한다.
- 자팀 선수는 11명으로 고정한다.
- 상대팀 좌표(`opponentPositions`)는 선택 항목이며, 입력할 경우 11명 전원을 요구한다(부분 입력 불가).
- 모든 국면(base/attack/defense)은 동일한 `players` 목록의 모든 선수에 대한 좌표를 가져야 한다.
- JSON 가져오기 시 스키마 검증(타입/필수 필드/좌표 범위)을 클라이언트(TypeScript)와 서버(Pydantic) 양쪽에서 수행한다.
- DB 저장 시 FK 무결성을 강제한다(분석 삭제 시 하위 선수·좌표 데이터 함께 삭제).

### 4.5 운영
- MVP는 공개 배포하지 않고 PC에서 로컬 실행한다. 프론트(Vite, 5173)와 백엔드(uvicorn, 8000)를 각각 기동한다.
- 실행 절차는 README에 명시하며, 가능하면 단일 스크립트로 동시 기동할 수 있게 한다.
- DB 파일(`tacticore.db`)은 로컬 파일이므로, 파일 복사로 백업한다. Git에는 커밋하지 않는다(`.gitignore`).
- 별도 서버 로그/모니터링 체계는 MVP 범위에서 다루지 않는다(FastAPI 기본 로그 사용).

## 5. 데이터 모델 개요 (MVP)

### 5.1 분석 데이터 JSON 스키마

아래 구조는 JSON 내보내기/가져오기(FR-07)의 파일 포맷이자, API 요청/응답 본문의 형식이다.

```json
{
  "schemaVersion": 1,
  "match": {
    "matchName": "string",
    "homeTeam": "string",
    "awayTeam": "string",
    "matchDate": "YYYY-MM-DD",
    "competition": "string",
    "analyzedTeam": "home | away"
  },
  "formation": "4-3-3",
  "players": [
    {
      "id": "string",
      "name": "string",
      "number": 0,
      "role": "string"
    }
  ],
  "phases": {
    "base": {
      "positions": [{ "playerId": "string", "x": 0, "y": 0 }],
      "opponentPositions": [{ "x": 0, "y": 0 }],
      "pressingLineY": 0,
      "comment": "string"
    },
    "attack": {
      "positions": [{ "playerId": "string", "x": 0, "y": 0 }],
      "opponentPositions": [{ "x": 0, "y": 0 }],
      "pressingLineY": 0,
      "comment": "string"
    },
    "defense": {
      "positions": [{ "playerId": "string", "x": 0, "y": 0 }],
      "opponentPositions": [{ "x": 0, "y": 0 }],
      "pressingLineY": 0,
      "comment": "string"
    }
  },
  "summary": "string"
}
```

| 필드 | 필수 | 설명 |
| --- | --- | --- |
| `schemaVersion` | O | 스키마 버전. 향후 구조 변경 시 마이그레이션 판단 기준 |
| `match` | O | 경기 기본 정보 (매치명, 홈/원정팀, 경기일자, 대회명, 분석 대상 팀) |
| `formation` | O | 초기 배치에 사용한 포메이션 프리셋 (예: `4-3-3`) |
| `players` | O | 자팀 11명의 이름, 등번호, 기본 역할 |
| `phases.*.positions` | O | 국면별 자팀 11명 좌표 (x, y는 0~100 백분율) |
| `phases.*.opponentPositions` | X | 상대팀 11명 좌표. 있으면 오버로드 레이어 활성화, 없으면 비활성 |
| `phases.*.pressingLineY` | X | 압박 라인 높이(y, 0~100). 미지정 시 자팀 최후방 라인에서 자동 산출 |
| `phases.*.comment` | O | 해당 국면의 전술 코멘트 |
| `summary` | O | 전체 분석에 대한 종합 평가 텍스트 |

### 5.2 DB 테이블 개요 (SQLite)

| 테이블 | 주요 컬럼 | 설명 |
| --- | --- | --- |
| `analyses` | `id`(PK), `match_name`, `home_team`, `away_team`, `match_date`, `competition`, `analyzed_team`, `formation`, `summary`, `schema_version`, `created_at`, `updated_at` | 분석 1건 = 1행. 목록 조회의 기준 테이블 |
| `players` | `id`(PK), `analysis_id`(FK), `name`, `number`, `role` | 분석별 자팀 11명 |
| `phases` | `id`(PK), `analysis_id`(FK), `phase_type`(base/attack/defense), `pressing_line_y`, `comment` | 분석당 3행 |
| `positions` | `id`(PK), `phase_id`(FK), `player_id`(FK, nullable), `side`(own/opponent), `x`, `y` | 국면별 선수 좌표. 상대팀은 `player_id`가 null이고 `side=opponent` |

- `analysis_id`, `phase_id` FK는 `ON DELETE CASCADE`로 설정해 분석 삭제 시 하위 데이터가 함께 제거되도록 한다.
- 목록 조회는 `analyses` 테이블만 조회하며, 상세 조회 시에만 하위 테이블을 조인한다.

> 좌표 데이터를 정규화하지 않고 `analyses.payload_json` 한 컬럼에 JSON 그대로 저장하는 단순안도 가능하다. MVP 일정이 촉박할 경우의 대안이며, 2단계 설계서에서 최종 확정한다.

### 5.3 API 엔드포인트 개요

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| `GET` | `/api/health` | 서버 가용성 확인 (§3.8의 폴백 판정용) |
| `GET` | `/api/analyses` | 저장된 분석 목록 조회 |
| `GET` | `/api/analyses/{id}` | 분석 상세 조회 (§5.1 JSON 형식으로 반환) |
| `POST` | `/api/analyses` | 새 분석 저장 |
| `PUT` | `/api/analyses/{id}` | 기존 분석 덮어쓰기 |
| `DELETE` | `/api/analyses/{id}` | 분석 삭제 |

> 상세 요청/응답 규격은 `3단계_기술_규격_및_API.md`에서 확정한다.

## 6. 리스크 / 이슈

- 모핑 애니메이션이 전술 정보를 명확히 보여주지 못하고 단순한 시각 효과처럼 보일 수 있음.
- 공간 레이어(5채널/하프스페이스/압박라인/오버로드)가 많아질수록 화면이 복잡해져 초보 사용자에게 부담이 될 수 있음.
- **일정 리스크**: 백엔드(FastAPI + SQLite) 도입으로 원문 Notion 일정(7~11일) 대비 2~3일이 추가될 것으로 예상됨. 일정이 촉박할 경우 §5.2의 `payload_json` 단순 저장안으로 축소하거나, FR-08(DB 저장)을 마지막 순서로 두고 나머지 MVP를 먼저 완성하는 순서를 권장.
- **운영 부담**: 사용할 때마다 백엔드 서버를 기동해야 하며, 서버 미기동 시 저장/목록 기능이 동작하지 않음 (§3.8에서 폴백 동작 규정).
- **배포 계획 변경**: 백엔드가 생겨 Vercel 정적 배포만으로는 전체 앱을 공개할 수 없음. MVP는 로컬 실행 전용이며, 공개 배포 방식은 2차에서 결정 필요.
- html-to-image로 Framer Motion 변환(transform)이 적용된 노드를 캡처할 경우 애니메이션 중간 상태가 캡처될 수 있음 (§3.5에서 애니메이션 완료 후 캡처로 대응).
- 상대팀 좌표 입력은 자팀 11명에 더해 11명을 추가 입력해야 하므로 작성 부담이 2배가 됨 — 오버로드 레이어 사용률이 낮을 수 있음(선택 입력으로 완화).
